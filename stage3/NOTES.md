# Stage 3 recorder: readings of the pre-registration

The frozen pre-registration (`docs/stage3/PREREGISTRATION_stage3.md`, sha256 `a62576a8…c515`) is not edited. Where it leaves a recording detail open, the reading taken in `stage3/` is listed here, with the main alternative. None was chosen by looking at data: the code was written against synthetic responses, and the only live data it has touched is the counts-only pilot. Items marked **(material)** could plausibly move a result. The analysis readings are in `analysis/NOTES_stage3.md`.

1. **(material) Where `index_after` sits.** The pre-registration says: chain and `index_before` first, "then the Kalshi requests, then a second index read". Read here as: per coin, `index_after` follows the Kalshi **market list** (the top of book that T1 trades on and that the validity rule synchronises). The hourly order books (for T2) come after both coins, each with its own `t0`/`t1`. Putting `index_after` after the books would move the hedge start 5 to 20 s after the quote and make the 0.10% and row-sync rules drop more rows. The book timing is stored, so T2 can be checked against it.
2. **Order inside a coin:** chain, then `index_before`, then the list. The pre-registration lists the chain and `index_before` together; reading the index second puts it as close as possible to the Kalshi request, which matters because it is the forward for hourly closes.
3. **Slot phase `hh:m2:30` UTC** (stage 2 uses `m3:02`). The pre-registration fixes 5-minute snapshots, not their phase. This phase puts the snapshots 57.5, 52.5 … 2.5 minutes before each hourly close: 12 per hourly market, all inside the 2-to-60-minute row window, with none at the moment of a close. With `m3:02` the last snapshot would fall 1 min 58 s before the close and be outside the window. During the pilot it also keeps stage 3's Kalshi requests about 30 s clear of stage 2's.
4. **First live slot** is 2026-11-20 00:02:30 UTC (the first slot at or after 00:00 at this phase). The last is 2026-12-17 23:57:30. A live run may start up to 30 minutes early and wait. A day has 288 slots.
5. **The 1-minute poll** reads `btc_usd` then `eth_usd` on every whole minute (`hh:mm:00`), in a thread independent of the snapshot and the git push. The poll at `hh:00:00` is the index at the hourly close. A failed read is written with an empty price and an error; nothing is filled in. Between two GitHub runs (every 5 h 40 min) a minute or two is usually missing while the next run checks out.
6. **(material) Validity per coin** is stage 2's rule: chain and the Kalshi market list (its last page) finished within 5 s, index moved under 0.10% between `index_before` and `index_after`, and both returned something. Added: a market list that stopped before its last page (a failed page) makes the coin invalid, because a partial list can silently drop markets.
7. **Hourly market** = a KXBTCD/KXETHD market whose `event_ticker` does not end in `17`, as pre-registered. The pilot report lists every whole hour without an hourly event and says whether it is a 5pm ET close.
8. **Books:** "a two-sided quote inside 3 to 97¢" is read as 0.03 ≤ bid < ask ≤ 0.97 (stage 2's test, plus bid < ask). At most 110 s are spent on books per snapshot; if that runs out the snapshot says `books_truncated: true` and the remaining markets have no book (T2 loses those rows; T1 is unaffected).
9. **Deribit expiries within 3 days** means the 08:00 UTC expiry is at most 72 h after the snapshot's start.
10. **Inverse options only.** `get_book_summary_by_currency?currency=BTC|ETH&kind=option` returns Deribit's coin-settled options (prices in coin), the same chain stage 2 fits. USDC-settled options are not recorded.
11. **Fee check.** `data/series_meta.csv` logs the `fee_type` and `fee_multiplier` Kalshi reports for both series at every run. That shows whether the series' fee class changes, but it is not the fee schedule itself, which the pre-registration asks to re-check before the first live snapshot. That check is still open (the Kalshi site is blocked from Claude's container).
12. **Pilot data** goes to `stage3-pilot`, never to `stage3-data`, and every snapshot carries `"mode": "pilot"`. The analysis refuses any snapshot whose mode is not `live`. The pilot branch also holds 5pm KXBTCD quotes recorded while stage 2 runs. It should not be opened for anything but the counts report, and can be deleted once stage 2 is analysed.
13. **Pilot length: 48 hours** (to 2026-11-08 06:00 UTC), as `DESIGN.md` suggests. The pilot changes no rule. Its spread histogram goes next to the power statement, as the pre-registration says, through the deviations log only if it changes anything (it can't change a gate).
